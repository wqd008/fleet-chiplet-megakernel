# Fleet / Mirage 在 MI300X 上的移植指南

日期：2026-11-16
适用：`wqd008/fleet-chiplet-megakernel`，分支 `amd_mi350` → `mi300x-adaptation`
目标机器：AMD Instinct MI300X（gfx942），ROCm 7.14.x，Ubuntu 24.04

本文记录**把这份代码从 MI350 移植到 MI300X 所需的全部步骤**。所有步骤都在真机上做过，
不是推测。按顺序执行即可复现；配套脚本见 `experiments/setup_mi300x_env.sh`。

> **一句话总结**：这份仓库在 MI300X 上**不是"设个环境变量就能跑"**。需要修 6 处环境/依赖
> 问题、固定一个特定的 composable_kernel 提交、并改 4 处源码。其中 **composable_kernel 的
> 版本**和 **两项 MI350 硬编码假设**是最容易被漏掉、又最致命的。

## §B 继续修复 MoE（当前唯一的拦路石）

### B0. 现在的确切状态

| 配置 | 状态 |
|---|---|
| 稠密 Qwen3-8B | ✅ 完全正常 |
| MoE，bs=1，`USE_GANG=0` | ⚠️ 能跑完（≈17.0 ms/token），但**输出不是文本** |
| MoE，bs=32，任意 gang | ❌ 产出非法 token（tokenizer `OverflowError`） |

**两者都没通过正确性验证，所以这些数字一个都不能用。** B4 仍无结论。

### B1. 复现当前故障（3 条命令）

```bash
cd $MIRAGE_HOME && export AMDGPU_TARGETS=gfx942 MIRAGE_HOME=$PWD MIRAGE_ROOT=$PWD

# 打开逐层插桩（默认完全惰性）
rm -rf permanent_output_dir
USE_GANG=1 USE_GANG_MOE=0 DEBUG_MOE_MASK=1 \
  python demo/qwen3/demo_30B_A3B.py --use-mirage --model Qwen/Qwen3-30B-A3B \
  --max-num-batched-tokens 32 --max-num-batched-requests 32 \
  --max-seq-length 512 --max-new-tokens 64 --ignore-eos \
  --prompt "Explain RISC vs CISC architectures in detail." 2>&1 | grep -E "MOE_DBG|TOPK_DBG|LIN_DBG|RMS_DBG" | head -20
```

**bs=32 的预期观测（这就是故障指纹）**：

```
[TOPK_DBG]  rows=32 gate_in[0][0..7]: -nan -nan -nan -nan -nan -nan -nan -nan   ← gate 输出全 NaN
[MOE_DBG]   NE=128 nact=1 mask: 0 -1 -1 ... | route0: 8 8 8 8 8 8 8 8           ← 路由塌缩成 1 个专家
[LIN_DBG]   B=32 K=2048 OSIZE=64 OSTRIDE=128 | in0=-nan w0=0.015442 out0=-nan  ← 权重正常，输入已 NaN
[RMS_DBG]   in[0]=-0.001007 in[1]=-0.038818 ... in[2047]=0.010986              ← rmsnorm 输入完全干净
```

**把 bs 换成 1 再跑一次**，会看到 `TOPK_DBG` 变成真实数值（`-4.0625 -3.859 ...`）—— 故障与 batch 相关。

### B2. 因果链（已确立）

```
rmsnorm 输入干净  →  rmsnorm 输出缓冲写入前是 0.0  →  gate 却在缓冲基址读到 NaN
                  →  logits 全 NaN  →  top-k 平局判据失效  →  8 槽位全投专家 0
                  →  nact=1  →  MoE 实际只算 1 个专家  →  NaN 经残差流污染所有下游层
                  →  lm_head 输出 NaN  →  argmax 给出越界 token id  →  tokenizer OverflowError
```

指针核对显示 gate 的 `in_ptr` **就是** `rmsnorm_out` 的基址，rmsnorm 各 block 的 `out_ptr`
也落在同一缓冲区内 —— **指针自洽，所以是任务完成序的问题，不是张量绑错。**

### B3. 已经排除的可能（别再重复试）

| 假设 | 怎么排除的 | 结论 |
|---|---|---|
| NT store 可见性 | 把 rmsnorm 的 non-temporal store 换成普通 store | ✗ 无效（保留为 `MPK_RMSNORM_USE_NT_STORE` 可切回） |
| 路由 kernel 清零自己输入的写-写冲突 | 用 `MPK_MOE_TOPK_ZERO_INPUT` 护卫掉那段落 | ✗ 无效 |
| gate 的 grid/block 不对 | 对齐稠密 demo（grid=输出维//64、block 128） | ✗ 无效 |
| `moe_gate_out` 未初始化 | 换成 host 侧零初始化张量 | ✗ 仍是 NaN |
| 权重坏了 | `w0=0.015442` 正常 | ✗ |
| 是 attention 或稠密部分坏了 | 稠密 demo 同构建完全正常 | ✗ |

### B4. 下一步：按这个顺序试（**先试 1**）

**① 每层独立的 `rmsnorm_out`（首要怀疑，成本最低）**

怀疑依据：`rmsnorm_out` 是**单个张量被全部 48 层共用**（在 `demo_30B_A3B.py` 约第 328 行创建一次），
写-写与读-写依赖都可能因此退化；bs=1 时每层 block 少、调度简单所以侥幸正确。

改法：把 `rmsnorm_out` 的创建**移进层循环**，每层一个新张量。额外显存仅
`48 × 32 × 2048 × 2 B ≈ 6.3 MB`，可忽略。同样处理 `attn_proj_out` 之类被复用的张量（先只改
`rmsnorm_out` 单变量验证）。

```bash
# 改完立刻用 B1 的命令复现，看 TOPK_DBG 是否变成真实数值
```

**② 如果 ① 无效：看真实任务序**

用框架自带的 profiler 或 `MPK_ENABLE_DEVICE_TASK_TIMING` 打开任务耗时，确认 rmsnorm 任务与
gate 任务的实际先后。`persistent_kernel.cuh` 里已有 `[FWD_PASS]` 等打印可参考。

**③ 如果 ① 无效：把 gate 的 grid 改回 `(1,1,1)` 再试**

注意 §1.2 的 cutlass 修复与 grid 是**耦合**的（`grid_for_rmsnorm_linear_layer` 的返回值取决于
该开关）。之前单独试 `(1,1,1)` 是在 cutlass 仍为 True 的情况下做的，现在条件变了，值得重试。

**④ 兜底：绕开 `linear_layer`**

gate 只是 `(32,2048)×(2048,128)` 的小 GEMM。可以换成 `splitk_linear_layer` **并补一个归约层**
（注意：demo 现在的 `--splitk-gate` 路径**缺少归约**，写的是未归约的部分和，实测 gate logits 呈
`0 -nan 0 -nan` 交替 —— 这是另一个独立缺陷，别直接用它）。

### B5. 修好之后：正确性闸门（**必须先过这一关再谈性能**）

参照 `experiments/correctness_check.sh`（目前只覆盖稠密 demo，需要照抄一份 MoE 版本）：

1. 用 `demo_30B_A3B.py` **不带** `--use-mirage` 跑一遍，得到参考 token；
2. 带 `--use-mirage` 跑同样配置，取生成 token；
3. 逐 token 比对。**判定标准与稠密路径一致**：贪心解码下前若干十个 token 完全一致，
   之后因 bf16 打平而分歧是可接受的；**若前 10 个 token 就不一致，则实现仍是错的。**

> 顺带记录：稠密 Qwen3-8B 的正确性验证是**前 47 个 token 完全一致**，可作为参照。

### B6. 什么算成功

- `tokenizer.decode` 能打印出**连贯的生成文本**（不再只有 prompt）；
- 与 PyTorch 参考前 ≥10 token 一致；
- bs=32 不再 `OverflowError`。

三条全过，才回去做 B4。

**Part A 已知结论**（详见 `docs/results/2026-11-16-MI300X-执行情况.md` §5）：
- bs=32 下 `tile_n=128` 比硬编码的 64 快 6–8%，且 **wgm 四个取值上 4/4 全胜**；
- **Fleet 出厂默认 gang 比不用 gang 还慢 2.6%**（与 README 在 MI350 上的 1.23× 矛盾）；
- **最优参数随 batch 移动**：bs=1 的排名与 bs=32 完全相反（bs=1 默认快 9.1%）。

### C2. MoE 修好后：Part B 的顺序

```bash
bash experiments/b4_moe.sh          # B4：gang MoE / gang 非 MoE / 非 gang 三向对照
```

- **B4**（最基础，README 从未回答）：`USE_GANG_MOE=1` vs `USE_GANG=1 USE_GANG_MOE=0` vs 全关。
- **B3**：每 XCD 耗时分布。`TRACE_MOE=1` 会打印 `[MOE_DISPATCH] sched=/xcd=/worker=/expert_offset=`，
  已确认能打出 11520 条（48 层 × 240 任务），可直接用。
- **B5**：换 Mixtral-8x7B 作对照（专家大得多）。准入条件已核对：
  `28672 % 64 == 0` ✓、`4096 % 256 == 0` ✓，bf16 约 93 GB 放得下。

**Part B 已有的结构性结论**（**不依赖 MoE 跑通**，见 `2026-11-16-PartB-MoE归因.md`）：
- gang MoE 对**每个激活专家**做 M=`BATCH_SIZE` 的稠密 GEMM，只在 epilogue 按路由跳过写入；
- 行利用率实测 **bs=1 仅 6.25%（16× 浪费）**、bs=32 为 **33.3%**，小 batch 最严重；
- 但 roofline 显示它**强访存受限**（算术强度 32 vs ridge 353 FLOP/byte），浪费的算力大半被隐藏，
  **真正的杠杆是权重访存与调度，不是抠掉浪费的行**。

### C3. 价值最高的可选项：把 decode attention 移植到 gfx942

一次解决**两个**问题：消掉 66% 的 attention 稀释 + 解锁 bs=64。

要改的只有一个文件 `tasks/mi300/paged_attention_decode_minimal_mi300.cuh`（373 行），两处 intrinsic：

| 原 | gfx942 上怎么办 |
|---|---|
| `__builtin_amdgcn_mfma_f32_16x16x32_f16` | gfx942 只有 16x16x16 形式；拆成 2× `mfma_f32_16x16x16f16` 累加（数学等价） |
| `__builtin_amdgcn_ds_read_tr16_b64_v4f16` | 转置 LDS 读是 CDNA4 专有；需用普通 LDS 读 + 寄存器转置模拟，或改 V 的 LDS 布局 |

**验证方式**：`USE_CK_FMHA=1` 能编译只是第一步；必须比对它与 `USE_CK_FMHA=0` 的输出，并确认
bs=64 能跑（grid = (64, 8, 10) = 5120 > 4096 的限制随之解除）。

### C4. 交付物格式（沿用，别改）

- 结果一律追加到 `experiments/results/results.tsv`（driver 自动写，崩溃/超时也记一行）；
- 用 `python experiments/summarize.py` 出汇总 —— 它**按配置（不是按 tag）合并**，
  能跨 stage 汇总同一配置，并报告噪声下限；
- **必须保留负面结果**：编译失败的配置、bs=64 的 grid 超限、`m_tiles` 不整除 batch 的断言，
  这些本身就是"参数空间实际自由度"的证据。

## §D 纪律与陷阱（每次实验前扫一眼）

1. **每次改参数前必须 `rm -rf permanent_output_dir`** —— megakernel 按模式编译，不删会静默复用旧产物。
2. **`AMDGPU_TARGETS=gfx942` 必须在每个 shell 里 export** —— 源码默认 `gfx950`。
3. **`Decode: ... ms/token` 不是 decode-only TPOT**，而是 prefill+decode 合起来的每次迭代平均时间
   （`demo.py:1316-1326`）。**同一 batch 内可比，跨 batch 不可比。**
4. **噪声是实测的**：中位数 2.6%、最差 6.5%（13 个重复配置）。**单次测量不要下结论。**
5. **算路由统计时必须用差异化提示词** —— 提示词相近会让所有序列末位 token 相同，路由退化成
   固定几个专家，我第一版就因此测出 `num_activated=8`、利用率 100% 的假象。
6. **不要用均匀路由假设** —— 路由是**偏斜**的（头部专家占 10.75%），均匀假设会给出 13.9× 的
   错误浪费倍数，实测 bs=32 是 3.31×。
7. **MoE 相关**：路由 kernel 单 block 覆盖 64 行（已从 16 改上来），batch 再大要同步调
   `WARPS_PER_CTA` 与 `block_dim`；`m_tiles` 必须整除 batch。
8. attention 占 bs=32 迭代约 **66%**，会把 gang 的相对收益稀释约 3 倍 —— 解读 A 部分结论时
   要换算到 linear 部分（`experiments/attention_share.md`）。

### 1.2 装 PyTorch（ROCm 版）

镜像没有 torch，必须自己装。选与项目匹配的版本：

```bash

```

可选的 wheel 索引：`rocm6.4`(torch 2.9.x)、`rocm7.0`(2.10.0)、`rocm7.1`(2.12/2.13)。
选 7.0 是因为它与计划里写的 "PyTorch 2.10.0" 一致。

> 注意这是**两套 ROCm 并存**：torch wheel 自带 HIP 7.0.51831，而 megakernel 用系统
> `/opt/rocm` 的 hipcc（7.14.1）编译。可以正常工作，但排查问题时要知道。

验证：


### 1.3 补 ROCm 的 cmake 开发文件（关键，且要绕开 apt）

cmake 配置 HIP 语言时需要 `hip-lang-config.cmake`，镜像只装了运行时没装开发文件。

### 1.6 补 git 子模块（`.gitmodules` 有、树里没有）

`.gitmodules` 列了 4 项，但 **`git submodule status` 是空的** —— 树里根本没有 gitlink。

`deps/` 下只有 `rocblas`）。所以只能手工拉：

```bash
cd <repo>
fetch_dep() {  # $1=名字 $2=url $3=sha
  mkdir -p "deps/$1" && cd "deps/$1"
  git init -q . && git remote add origin "$2"
  git fetch -q --depth 1 origin "$3" && git checkout -q FETCH_HEAD
  cd <repo>
}
```

`deps/z3` **不需要** —— `setup.py` 用的是 `z3-solver` wheel。

## 2. composable_kernel：必须固定到特定提交（最容易踩的坑）

Fleet 的 MI300 kernel 会 `#include` `deps/composable_kernel/include` 下的 `ck_tile`，
源码注释写着 **"must come before system CK"**。原因：**ROCm 7.14 自带的系统 CK 与 Fleet
手写的 policy 不兼容**，报错形如

```
gemm_pipeline_ag_bg_cr_base.hpp:283: error: no member named 'MakeADramTensorView'
    in 'kernel::GemmPipelineSmallTilePolicy<16, 64, 256>'
```

### 2.1 怎么定位到正确提交（可复用的方法）

用两个**互相夹逼**的 API 标记（脚本见 `experiments/find_ck_commit.py`）：

| 标记 | 说明 |
|---|---|
| `kHasSink` in `TileFmhaFwdSplitKVTraits` | Fleet 传 **14 个模板参数**（第 14 个是 `kHasSink`），所以 CK 必须有它 |
| `Policy::template is_a_load_tr` in `gemm_pipeline_ag_bg_cr_base.hpp` | Fleet 的 policy **没有**这个成员，所以 CK 必须**还没**要求它 |

逐个 tag 探测的结果：

| CK 参考点 | FMHA traits | GEMM 要求 `Policy::is_a_load_tr` | 结论 |
|---|---|---|---|
| rocm-7.0.0 / 7.0.2 | 13 参数，无 `kHasSink` | 否 | 太旧 |
| rocm-7.1.x / 7.2.x | 13 参数 | 否 | 太旧 |
| therock-7.9.0 / 7.10 | 13 参数 | 否 | 太旧 |
| **`ac18460782fa`（develop）** | **14 参数，有 `kHasSink`** | **否** | ✅ **匹配** |
| 下一个 develop 提交 `717f2efe` | 14 | **是** | 太新 |
| 系统 ROCm 7.14 | 14 | **是** | 太新 |

**结论：必须固定在 `ac18460782fadcd24aa321394c63dc284c90593b`。** 它同时满足两个约束，
且是满足约束的**最新**提交（最接近 Fleet 开发时的快照）。**只差一个提交就会编译失败。**

### 2.2 拉取（稀疏，只取 include/，114 MB）

```bash
mkdir -p deps/composable_kernel && cd deps/composable_kernel
git init -q . && git remote add origin https://github.com/ROCm/composable_kernel.git
git sparse-checkout init --cone && git sparse-checkout set include
git fetch -q --depth 1 origin ac18460782fadcd24aa321394c63dc284c90593b
git checkout -q FETCH_HEAD
```

> **不要**把 `deps/composable_kernel` 升级到更新的 tag，也**不要**让 `/opt/rocm/include`
> 抢先出现在 include 顺序里。

## 4. 源码需要改的地方

### 4.1 `AMDGPU_TARGETS=gfx942`（**必须显式设置**）

`python/mirage/mpk/persistent_kernel.py:350`：

```python
amdgpu_target = os.environ.get("AMDGPU_TARGETS", "gfx950")   # ← 默认是 MI350
```

不设就会编出 MI300X 上跑不了的产物。**每次运行前都要 export。**

### 4.2 gang 路径**不需要**改（好消息）

`persistent_kernel.py:425-427` 在 ROCm 下恒设 `self.target_cc = 94`，而所有 gang 层的门禁都是
`assert self.target_cc == 94`。所以 **gang 路径在 MI300X 上自动启用**，不用动代码。

### 4.3 `USE_CK_FMHA=1`：一个文件用了 gfx950 专属指令

`include/mirage/persistent_kernel/tasks/mi300/paged_attention_decode_minimal_mi300.cuh`
（文件名带 `_mi300`，内容却是 MI350）：

```
:27  __builtin_amdgcn_mfma_f32_16x16x32_f16   needs target feature gfx950-insts
:47  __builtin_amdgcn_ds_read_tr16_b64_v4f16  needs target feature gfx950-insts
```

两条都经编译实测确认是 gfx950 专属：16x16x16 的 f16 MFMA 在 gfx942 上可以编译，
**16x16x32 的不行**；`ds_read_tr`（转置 LDS 读）是 CDNA4 才有的指令，**gfx942 上根本不存在**。

**全仓只有这一个文件**用了 gfx950 专属 intrinsic。

已实现的移植（分支 `mi300x-adaptation`，都包在 `#if defined(__gfx950__)` 内，MI350 行为不变）：

- `tasks/mi300/task_header.cuh`：只在 gfx950 时 include 该文件；
- `paged_attention_ck_fmha_split_kv_mi300.cuh`：非 gfx950 时 `seqlen_q == 1` 改走
  `paged_attention_ck_fmha_prefill`（它把 `seqlen_q` 当运行期参数收）。

> **但这只是让它能编译，性能反而更差**：实测 bs=1 下 `USE_CK_FMHA=0` 是 10.207 ms/token，
> 走这个替换路径是 15.390 ms/token —— 因为替代品用 prefill 形状的 kernel 每步重算整个 KV，
> 随上下文线性增长（iter 1 约 10.0 ms → iter 1100 约 20.7 ms），而原 kernel 是平的
> （约 10.1 ms）。**真正的修法是把 `paged_attention_minimal_decode` 移植到 gfx942**
> （2× 16x16x16 MFMA + 寄存器转置替代 `ds_read_tr`），这仍是未完成项。

**当前 A 部分实验全部使用 `USE_CK_FMHA=0`**，它无需改任何 kernel 代码且更快。

### 4.4 MoE demo 的两处 MI350 硬编码（`demo/qwen3/demo_30B_A3B.py`）

这两处让 `demo_30B_A3B.py` 在 MI300X 上**第一次迭代就 `HIP error: an illegal memory access`**：

**(a) lm_head / argmax 的 grid 按 worker 数分配。**
padding 后 `vocab_size = 153600`，按 worker 数切分：

| 平台 | CU | scheduler | worker | `153600 % worker` |
|---|---|---|---|---|
| MI350 | 248 | 8 | 240 | 0 ✅ |
| MI300X | 304 | 8 | **296** | **272** ❌ |

`demo/qwen3/demo.py:511` 早有保护，MoE demo 没有。**照搬即可**：

```python
argmax_tasks = mpk.num_workers if vocab_size % mpk.num_workers == 0 else 240
```

并把三处 `mpk.num_workers`（`argmax_part_value`/`argmax_part_index` 的 dims、lm_head 的
`grid_dim`、`argmax_partial_grid_dim`）换成 `argmax_tasks`。

**(b) `use_cutlass_kernel` 没在 ROCm 上强制关闭。**
`demo.py:156` 有：

```python
if getattr(torch.version, "hip", None):
    args.use_cutlass_kernel = False
```

注释写明 CUTLASS 需要 CUDA tensor core，**且该开关同时决定 `grid_for_rmsnorm_linear_layer`
的返回值**（关闭时返回 `size//64`）。MoE demo 没有这段，实测以 `True` 在 MI300X 上运行。

### 4.5 MoE 路由 kernel 的行覆盖上限

`moe_topk_softmax_mi300.cuh`：`ROWS_PER_WARP = (64×8)/128 = 4`，`WARPS_PER_CTA = 4`
→ 每个 block 只覆盖 **16 行**；而 demo 用 `grid_dim=(1,1,1)` 启动
→ **batch > 16 的行永远拿不到路由**。

已改：`WARPS_PER_CTA` 4 → 16（`src/kernel/task_register.cc`），demo 的 `block_dim`
256 → 1024（16 warp × 64 线程），覆盖 64 行。

### 4.6 一个仍**未解决**的排序问题（bs=32）

插桩（`DEBUG_MOE_MASK=1`）显示：bs=32 时 MoE gate 读到的是 rmsnorm **尚未写入**的
`rmsnorm_out`（gate 的 `in0 = -nan`，而 rmsnorm 的输入完全干净、缓冲写入前是 0.0、指针自洽）。
后果是 logits 全 NaN → top-k 平局 → 全投专家 0 → MoE 塌缩成单专家。

bs=1 时同样插桩显示 logits 是真实数值，所以**只在大 batch 出现**。
首要怀疑：`rmsnorm_out` 是**单个张量被全部 48 层共用**，写-写/读-写依赖因此退化。
下一步可试「每层独立缓冲」。

## 7. 附录：本次移植的踩坑顺序（供下次判断优先级）
