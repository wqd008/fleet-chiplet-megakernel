## 1. 为什么 MoE 是芯粒问题的正解

### 1.1 重新表述：MoE 的瓶颈是搬移，不是算力

前一版把 MoE 的问题表述为"数据相关基数导致 tile 几何错配"。这个表述正确但不够本质。更准确的表述是：

> **稠密解码的瓶颈是"把权重从 HBM 搬到 SM"；MoE 的瓶颈是"把 token 搬到专家、把专家重量搬到 token"。**
> 前者是一对多的流式读取（同一份权重喂所有 SM）；后者是**多对多的交换**（token 按路由散到不同专家，专家权重按激活散到不同 XCD）。

**关键区别**：稠密的搬移模式是**广播**——一份权重，所有读者按同一顺序读，缓存与访问序都能优化。MoE 的搬移模式是**散布再聚集**（scatter-gather）——搬移的目标由运行期路由决定，**没有稳定顺序可优化**。

### 1.2 芯粒为什么让 MoE 的问题更尖锐

| | 片内（单 die） | 跨 XCD |
|---|---|---|
| 搬移代价 | L2 分片延迟低、带宽足 | Infinity Fabric，**带宽远低于片内，延迟高一个量级** |
| 缓存作用 | 一份数据被所有 SM 复用 | **L2 按 XCD 分区，跨 XCD 复用失效** |
| 同步 | 一条 fence 全搞定 | **MI300X 上 L2 跨 XCD 不一致，必须 release fence + L2→HBM 回写** |

**把这三条与 §1.1 合起来**：MoE 的 scatter-gather 搬移模式**恰好是片内缓存最帮不上忙、跨 die 链路最吃不消的模式**。稠密解码至少还能靠"同一份权重被 30 个 worker 共享"摊薄搬移成本；MoE 的 token 一番散开后，每个 XCD 拿到的 token 子集不同、要读的专家权重也不同，**共享的前提直接消失**。

**所以"MoE 需要芯粒专用优化"这个判断成立，而且理由比"Fleet 没做好"强得多**：不是因为别人没做，是因为**搬移模式的数学性质变了**。

### 1.3 一个算例（算术，未实测）

Mixtral-8x7B，单层，B=32，top-2，bf16：

| 搬移对象 | 量 | 说明 |
|---|---|---|
| 专家权重（读） | **704 MB / token** | top-2 × 352 MB |
| 激活搬移（若走专家分片） | **512 KB / token** | `B × k × hidden × 2B = 32×2×4096×2` |
| 比值 | **0.07%** | 搬移激活几乎免费，**省下的是权重读取** |

**这个 0.07% 是本方向的核心论据**：MoE 里搬 token 的代价远小于搬权重的代价。所以"把 token 送到专家所在处"在算术上显然是划算的——**除非**权重读取本来就不重复（8 个 XCD 读同一份权重不产生 8 倍 HBM 流量）。

**而这正是必须实测的那个点**：地址哈希把同一份权重固定映射到某个 L2 分片，8 个 XCD 同时读它时，请求都挤过那一个分片的出口。**全播方案是否因此浪费了带宽，是 §3.1 微基准要回答的唯一问题。**

## 2. 第一步：在 MI300X 上复现 Fleet 的 MoE 并做瓶颈归因

**为什么这是第一步**：我们目前关于 Fleet MoE 的一切都是代码推断。而 §1.3 的论据、§4 的路线选择，全部取决于"Fleet 的 MoE 实现到底卡在哪"。**在花任何设计精力之前，先让它在真机上跑起来并测出瓶颈。**

### 2.2 MoE 复现（这是本轮的重点）

代码里有 `demo/qwen3/demo_30B_A3B.py`，用 **Qwen3-30B-A3B**（128 专家、激活 3B、中间维 768）。README **没有**给出 MoE 的命令与结果——**这是需要我们自己补齐的部分**。

```
① 先确认它能否跑通（这是"Fleet 有没有可信 MoE 基线"的唯一判据）
② 跑通后与稠密对照：TPOT、以及 Fleet/MPK 的比值
③ 记录：专家分布（每专家 token 数的直方图）、每 XCD 的专家处理序列、
       是否触到任何 assert（尤其 total_tiles_per_xcd <= 65535）
```

**注意 Qwen3-30B-A3B 是**极小专家**（3.15 MB/专家、0.39 MB/专家/XCD），是 §1.3 里最有利的一档。**它跑得好不代表 MoE gang 成立。** 必须至少再加一个 Mixtral 级的中等专家模型作对照——Fleet 的 `Gang MoE linear only supported on MI300/MI350` 断言不排除 Mixtral 形状，但 `assert output_size % tile_n == 0` 与 `assert reduction_size % 256 == 0` 可能挡住。

### 2.3 瓶颈归因：测什么、怎么测

复现本身只是手段。**这一步的产出是"Fleet 的 MoE 卡在哪"的判断。** 按信息量排序：

| # | 测量 | 回答什么 | 入口 |
|---|---|---|---|
| **A1** | **每专家实际 token 数直方图**（运行期统计路由） | 验证 P1 错配有多大。Mixtral：B=32 时均值 8、方差多大？最热专家多少 token？ | 在 routing kernel 后加一次统计，或 host 侧 dump `moe_routing_indices` |
| **A2** | **M-tile 行利用率**（有效 token 行 / 处理的 16 行） | P1 的直接量化。**预期 B=8 时 12.5%、B=32 时 50%** | 需要设备端计数，或从 A1 推算 |
| **A3** | **专家→XCD 的负载分布**（每 XCD 处理多少 tile、耗时多少） | P6：固定 `(E+7)//8` 轮询是否造成尾延迟 | `MPK_ENABLE_DEVICE_TASK_TIMING` 已有逐任务计时（`gang_linear_mi300.cuh:94-100` 的 `s_memrealtime`），MoE kernel 同样内建 |
| **A4** | **同一权重被 n 个 XCD 同读时的有效带宽**（n=1..8） | **§1.3 的核心机制假设**：全播是否浪费带宽 | 独立微基准，见 §3.1 |
| **A5** | **cross-XCD fence 次数与耗时** | 分层同步在 MoE 下是否仍划算（MoE 的 expert 循环比稠密多一层） | `buffer_wbl2` 计数；可用 rocprof |

**A1–A3 只需跑通 MoE 就能拿到**，成本低、信息量大。**A4 是独立微基准，但它回答的是本方向最根本的机制问题。**

### 2.4 这一步如何决定后续

| A1/A2 的结果 | 解读 | 决策 |
|---|---|---|
| 行利用率在常见 batch 下 < 60% | P1 成立且值钱 | **进入 §4 的路线一**（几何档位） |
| 行利用率 > 85%（路由比预期均匀） | P1 影响有限 | 转向**路线二**（专家分片）与 A4 |
| A4 显示带宽随 n 快速饱和 | 全播确实浪费带宽 | **路线二成为主攻** |
| A4 显示带宽随 n 线性扩展 | 全播不浪费 | **路线二失去机制基础**，回到路线一/三 |
| MoE 根本跑不通 / 触及 assert | Fleet 的 MoE 只是半成品 | 这本身是重要发现；转向自建 baseline |

## 3. 微基准：两个需要独立测量的硬件事实

这两条与 Fleet 无关，是"芯粒上做 MoE"的地基。**它们都是纯微基准，工作量小，但决定 §4 的路线选择。**

### 3.1 地址哈希下的 L2 分片出口带宽

**问题**：n 个 XCD 同时读同一段权重（n = 1..8），有效带宽随 n 如何变化？

**为什么关键**：如果权重地址被哈希到固定的 L2 分片，那么 n 个 XCD 的读请求都汇聚到同一个分片的出口。**若带宽在 n=2 就饱和，全播方案（每个 XCD 读全部专家）就浪费了 (n−1)/n 的带宽**——这是"专家分片"路线的全部理由。

**设计**：分配一段远大于 L2 的 buffer（避免命中），让 n 个 XCD 上的 worker 以相同顺序读它，测聚合带宽。n = 1, 2, 4, 8。

**对照**：
- 让各 XCD 读**不同**的 buffer（无汇聚）——测出的应该是带宽上限；
- 让各 XCD 读**同一** buffer（有汇聚）——测出的应是分片出口上限；
- 两者之比 = 全播的带宽损失。

**读法**：若"同 buffer"的带宽在 n=2 后不再增长，说明单分片出口是瓶颈。**注意这不能直接推广到"专家分片一定更好"**——还要看权重总读取量是否真的减少。

### 3.2 跨 XCD 的激活搬移代价

**问题**：把 `B × k × hidden × 2B` 的激活从若干 XCD 搬到另一个 XCD，代价是多少？

**为什么关键**：§1.3 算出激活搬移只占权重的 0.07%，但那是**字节数**之比。**跨 die 的链路延迟远高于片内**——所以即使字节少，**发起次数与延迟**可能才是成本。MoE 的 token 路由会产生大量小消息（每个 token 到每个目标专家的激活是 `hidden × 2B = 8 KB`，Mixtral）。

**设计**：测 8 KB / 64 KB / 512 KB 三种消息在 XCD 间搬移的延迟与带宽，对比片内。

**读法**：若小消息的**每消息固定开销**很高（如 2 µs），那么 `B×k = 64` 条消息就是 128 µs——**与一次专家 GEMM 同量级**。这会**推翻 §1.3 的乐观结论**，并把路线二从"显然划算"变成"需要谨慎设计消息聚合"。

**这条是本轮最重要的诚实性检查**：我们目前所有关于"搬移便宜"的论据都是字节数，而芯粒上真正的成本可能是**消息数与延迟**。

## 4. 三条候选路线（按 §2/§3 的结果取舍）

前置提醒：**三条路线共享一个未解决的实现落差**——Fleet/Mirage 的 tile 几何是编译期模板常量。任何"让几何随形状变"的方案都需要一个 kernel 变体族 + 派发规则（CAKE 的形态，不是新发明）。

### 路线一：几何档位（若 A1/A2 显示错配严重）

**做法**：把 `MPerBlock` 从固定的 16 改成数据相关的档位（如 {4, 8, 16, 32}），由每专家 token 数选择；或采用 MonoMoE 式的轴交换（token 放到 tensor-core 的小 N 轴），使任意小 token 数都能打满。

**优点**：**可以在本机（gfx1100）先验证**——M 维错配与 die 数量无关。**它能单独否决或支持整个方向。**

**风险**：如果这仍然是"把一个常数换成另一个更好的常数"，就只是调参。要成为方法贡献，必须证明**档位随 shape/路由/硬件改变**。

### 路线二：专家分片 vs 全播（若 A4 显示带宽饱和）

**做法**：把"每个 XCD 处理全部专家"改成"专家常驻部分 XCD，token 路由过去"，并在 IR 里表达**数据归属与激活搬移**。

**优点**：**纯芯粒现象**（单卡上不存在），机制明确（地址哈希 → 分片出口），且**不需要改 kernel**（只改任务图与数据放置）。

**风险**：依赖 A4；且 §3.2 可能显示消息数开销抵消收益。

### 路线三：路由感知的专家几何包（与一、二互补）

**做法**：离线统计路由分布，按预期 token 数给专家分档（热/温/冷），每档配不同几何与放置（热专家大 MBlock + 复制；冷专家小 MBlock + 合批）。

**优点**：把"几何应由路由分布决定"变成一个**可测量的关系**。路由分布是模型与负载的稳定属性，值得固化。

**风险**：需要运行时采样。RaMP 的先例是在已有的 token-grouping kernel 里做，成本 <1 µs——**可行，但要工程**。

## 5. 打开场景：还有哪些负载提出结构上不同的需求

前面几轮讨论的负载（attention、MoE）都来自 LLM 解码。要把方法做成"megakernel 生成"而不是"Qwen3 生成"，必须看结构上不同的负载。**我不追求罗列，只挑那些会打破当前方法假设的。**

### 5.1 判断框架：负载打破的是哪一条假设

Fleet 与我们的方法都隐含四条假设。按"破坏哪一条"分类：

| 假设 | 含义 | 破坏它的负载 |
|---|---|---|
| **H1 复用模式是"读一次、多读者"** | 数据被多个消费者重复读，缓存有意义 | **循环状态**（读-改-写）、**流式/一次性**数据 |
| **H2 工作是静态且均匀可切的** | 任务图在编译期确定，各单元工作量相当 | **数据相关基数**（MoE 已在此）、**数据相关依赖**（稀疏求解） |
| **H3 依赖来自数据流** | 一个算子读另一个算子的输出 | **邻居/结构化依赖**（stencil、模板计算） |
| **H4 吞吐优先、延迟可容忍抖动** | 目标是最小化平均每 token 时间 | **控制回路**（尾部延迟与抖动是主指标） |

### 5.2 四个结构上不同的候选

#### (a) 循环状态 / 线性注意力 —— **破坏 H1**

**是什么**：Mamba、DeltaNet、Kimi Delta Attention 等把 KV cache 换成**固定大小的循环状态矩阵**，每个 token 做一次读-改-写。

**为什么结构不同**：注意力是**只读** KV（每个 token 读、不写回），所以可以任意分片、任意复制——这正是 Fleet gang attention 的思路。循环状态是**读-改-写**：

- **不能复制**（复制了要同步两个副本，比不复制的代价更高）；
- **必须串行**（token t 的状态是 t−1 的函数）；
- **状态转移是唯一的全局串行点**，而这个状态本身不大（`d_state × d_model`）。

**芯粒含义**：串行点意味着"状态必须只属于一个 XCD"，但**处理这个 token 的其余计算可以散布**——于是产生一个**新的跨层决策**：状态放哪个 XCD、其余计算怎么散布、散布的结果怎么汇回状态所在的 XCD。**这与 KV 复制是相反的决策结构**。

**值得关注的原因**：CAKE 已经在做 Kimi Delta Attention 的 kernel 生成（其摘要提到 FlashKDA 上 2.05× 几何平均加速）。**但 CAKE 是单 GPU 作用域**——"循环状态在多 XCD 上放哪"是它不会碰的问题。

**验证成本**：中（需要一个新的状态更新 task 类型，但数学简单）。

#### (b) 投机解码 —— **破坏 H2（工作量的数据相关性最强）**

**是什么**：一次验证 `γ` 个候选 token，接受 `a` 个（`1 ≤ a ≤ γ`）。

**为什么结构不同**：**每步的有效工作量由运行期决定，且`a` 的分布高度偏斜**（长尾）。这与 MoE 的"每专家 token 数"同类，但更极端：MoE 是**分散**（把 B 个 token 散到 E 个专家），投机是**收束**（γ 个候选收成 a 个被接受）。而且它天然是**两个模型协作**（draft + target），有 state handoff。

**芯粒含义**：接受率决定接受多少 token 可以并行验证；**门控逻辑必须由一个地方做，其余地方等待**——这是"控制流本身跨 die"的问题。

**已有工作**：WTS（Weights That Stay）已做投机解码的权重常驻（最高 11.6×）。**但 WTS 是单卡**。跨 XCD 的投机解码是空的。

**验证成本**：高（需要两个模型 + 接受循环）。

#### (c) Stencil / 结构化稀疏 —— **破坏 H3**

**是什么**：PDE 求解、模板计算、图算法。每个格点依赖**邻居**，不是"上游算子"。

**为什么结构不同**：**依赖是空间结构而非数据流**。这带来一个稠密 LLM 里完全不存在的概念：**halo（晕区）**——一个子域要被计算，必须先拿到邻居子域的边界数据。

**芯粒含义**：**这正是它的机会**——halo 交换是**固定形状、固定位置、小体积**的通信模式，而且**规律**。它比 MoE 的 scatter-gather 对芯粒友好得多。同时它给表示提出一个新要求：**子域相邻关系必须显式**（"我这个 tile 的 halo 来自那个 tile"），这比"这个边跨 die"更具体——它是**拓扑化的**。

**但必须诚实**：
- **科学计算在 GPU 上通常不需要 megakernel**——它的 kernel 少而重，launch 开销占比低，"省 250 次 launch"这个动机不成立；
- **合算的情形**：**多物理耦合**（流体 + 结构 + 传热交替迭代）或**强耦合的多阶段求解器**，那里确实有大量短 kernel 交替；
- **另一个真实约束**：科学计算要双精度、要可复现（bit-exact），这对 tile 与同步的设计约束比 LLM 严。

**结论**：**不是近期方向，但它是检验"方法可复用性"的最佳测试床**——如果表示只能表达"token 流经算子"，那它就不是以 megakernel 为对象的方法。

**验证成本**：高（要建一个非 LLM 的 baseline，且要证明 megakernel 在这类负载上本身有价值）。

#### (d) VLA / 具身智能控制回路 —— **破坏 H4**

**是什么**：视觉-语言-动作模型，作为机器人控制回路的一环，以固定频率（如 10–100 Hz）出动作。

**为什么结构不同**：**指标从吞吐变成延迟与抖动。**

- 回路有**硬截止时间**（100 Hz ⇒ 10 ms 预算），超时的后果是机械臂失控，不是"慢一点"；
- 输入是**传感器流**（图像帧 + 语言指令 + 本体状态），有**多模态融合**点；
- 动作输出是**低维小张量**，与之对比的是庞大的编码器——**算术强度极低**；
- 需要**跨帧的状态**（视觉历史、隐藏状态），但**不需要 KV cache 那么长**。

**芯粒含义**：**尾部延迟（p99）优先于均值**——这与 Fleet 优化的 TPOT 是**相反的目标**。这会给设计提出全新要求：

- **可预测性**：所有 XCD 的完成时间必须可界定（这正是 Fleet 的 8 次 fence 造成的不确定点）；
- **优先级**：编码器的一部分（安全关键）必须保证延迟，其余可以让路；
- **超时降级**：必须能在预算内交付一个次优动作，而不是等到算完。

**已有工作**：**我没有检索到这个方向上有 megakernel 工作**（见 §6 的检索说明）。这既可能是空白，也可能是"不需要"——**VLA 的模型可能太小，用 megakernel 划不来**，需要先确认模型规模。

**验证成本**：高（要有真实的控制回路与截止时间需求）。

### 5.3 我的排序

| 负载 | 破坏的假设 | 与芯粒的契合度 | 验证成本 | 建议 |
|---|---|---|---|---|
| **MoE** | H2 | **高**（scatter-gather 正是芯粒最痛的模式） | 中（可复用 Fleet 的 MoE 代码） | **主攻** |
| **循环状态 / 线性注意力** | H1 | 高（串行点上多出新的放置决策） | 中 | **第二**，与 MoE 并行调研 |
| **投机解码** | H2 | 中（控制流跨 die 是新问题） | 高 | 第三 |
| **Stencil / 结构化稀疏** | H3 | **高**（halo 是规律通信，对芯粒友好） | 高 | **长期测试床**，不作为近期产出 |
| **VLA / 控制回路** | H4 | 中（尾部延迟优先，与 Fleet 目标相反） | 高 | 需要先确认模型规模是否值得 |

**从这张表能得到一个对方法设计的结论**：

> MoE（H2）、循环状态（H1）、stencil（H3）、控制回路（H4）**各自破坏一条不同的假设**。
> 一个真正"可扩展"的 IR 应当在**不重写 lowerer 的前提下**容纳这四种。这就是"可扩展"的可验证定义——**不是"层数更多"，而是"新负载只增加词汇，不改动机制"**。

## 7. 执行顺序

```
第 0 步（现在，GPU-free）
  ├─ 定向检索：§5 四个候选方向是否已有 megakernel 工作（尤其 VLA）
  └─ 读 demo_30B_A3B.py，确认 Fleet 的 MoE 路径需要哪些前置条件

第 1 步（MI300X 到位）
  ├─ 复现稠密基线（§2.1 的配方），对齐 README 的 B=1/B=32/B=64 三个点
  └─ 确认复现误差在 5-15% 内（README 自己承认的范围）

第 2 步（MI300X）
  ├─ 跑通 MoE（demo_30B_A3B.py），记录能否跑通/是否触 assert
  ├─ A1–A3：每专家 token 直方图、行利用率、每 XCD 负载分布   ← 决定路线一
  └─ 若跑通，加一个 Mixtral 级中等专家模型作对照（Qwen3-30B-A3B 的专家太小，不具代表性）

第 3 步（MI300X，独立微基准）
  ├─ A4：地址哈希下的 L2 分片出口带宽（n=1..8）              ← 决定路线二
  └─ §3.2：跨 XCD 小消息的延迟（8 KB / 64 KB / 512 KB）      ← 检验 §1.3 的乐观结论

第 4 步（本机 + MI300X）
  └─ 路线一的最小验证（几何档位）——本机可先做一半，因为它与 die 数量无关

第 5 步（仅当第 2–4 步支持时）
  └─ 路线二/三与 IR 表示的设计
```

**最该先做的三件事**：**MoE 能否跑通**（决定有没有 baseline）、**A1/A2 的行利用率**（决定几何错配是否值钱）、**A4 的分片带宽**（决定专家分片这条路是否有机制基础）。

**最该避免的**：先设计 IR，再去验证它要表达的东西是否值钱。
