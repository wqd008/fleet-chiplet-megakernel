## 0. 直接回答

> **问题：MoE 算子用这套框架，所实现的性能是不是很 naive？还有足够的优化空间供我们研究？**

**答案分三层，第一层就足够定性：**

1. **MoE 路径在 MI300X 上根本跑不起来。** `demo_30B_A3B.py` 在 bs=1/8/16/32、gang 与非 gang 共 6 种组合下**全部**以 `HIP error: an illegal memory access` 崩溃，且发生在第一次 megakernel 迭代内。同一份构建、同一个 CK、同一个 harness 下，稠密路径（Qwen3-8B）完全正常。这不是"naive"，这是**未完成**。

2. **从代码结构看，它的几何与数据基数确实是错配的，而且已量化。** gang MoE kernel 对**每个被激活的专家**都做一个 M = BATCH_SIZE 的稠密 GEMM，只在 epilogue 里按路由跳过写入。有效行 / 实际计算行：
   - **bs=1：6.25%（16.0× 浪费）** —— 每个激活专家平均只收到 1 个 token，却要算一个 16 行的 tile
   - **bs=32：33.3%（3.3× 浪费）**
   
   **浪费在小 batch 最严重**，而这正是 decode 延迟最要紧的区间。计划 §0.1 的 P1 假设（`MPerBlock=16` 与数据相关基数错配）在真机上成立。

3. **但"浪费"是否可支付，取决于它落在 roofline 的哪一侧——答案是：目前基本被隐藏。** MoE 的算术强度是 32 FLOP/byte，机器 ridge 是 353 FLOP/byte，**强访存受限**。浪费掉的是算力（0.29 ms/iter at peak），而访存下限是 3.24 ms/iter，所以多算的部分大半藏在访存后面。**这意味着：真正该优化的是访存与调度，不是把浪费的行抠掉。**

**结论：优化空间足够大，但方向不是"修几何"这么简单。** 详见 §6。

## 1. 首要发现：MoE 路径无法运行

### 1.1 证据

| bs | `USE_GANG_MOE=1` | `USE_GANG_MOE=0` |
|:---:|:---:|:---:|
| 1 | 非法访存 | 非法访存 |
| 8 | 非法访存 | 非法访存 |
| 16 | 非法访存 | 非法访存 |
| 32 | 非法访存 | 非法访存 |

所有 6+ 种组合失败方式一致：

```
torch.AcceleratorError: HIP error: an illegal memory access was encountered
```

（Python 堆栈落在 `ender.record()`，是异步上报；真正的越界在更早的 megakernel 内。）

### 1.2 已排除的原因（重要，用于界定这是 Fleet 的问题而非环境问题）

| 假设 | 如何排除 | 结果 |
|---|---|---|
| 环境/构建坏了 | 同一 venv、同一份 `deps/composable_kernel` 固定提交，跑稠密 Qwen3-8B 冒烟测试 | **exit=0，正常出数**（15.513 ms/token，`USE_CK_FMHA=1`） |
| 模型/harness 坏了 | 同一命令去掉 `--use-mirage` 走 PyTorch 路径 | **exit=0** |
| CK FMHA 的锅 | MoE demo 的 `USE_CK_FMHA` **默认就是 0**，且失败与 gang 无关 | 排除 |
| batch 太小的锅 | bs 从 1 试到 32 | 全部失败 |
| 页配置的锅 | 换 `--max-num-pages 256 --page-size 64` 重试 | 同样失败 |
| MoE 任务根本没派发 | `TRACE_MOE=1` | 打印了 **11520 条 `[MOE_DISPATCH]`**（= 48 层 × 240 个 W13 任务），说明任务确实派发并开始执行，崩溃发生在**执行期** |

### 1.3 这不是一个"没人踩过"的角落——它是**没人测过**的角落

- **`README.md` 完全没有提到 MoE / 30B demo / `USE_GANG_MOE`**（已比对上游 `ROCm/fleet-chiplet-megakernel` 的 README，同样没有）。
- **`.github/workflows/` 下没有任何 job 调用 `demo_30B_A3B.py`**（`grep -rn "30B" .github/` 无结果）。

这与计划 §0.1 的判断一致：Fleet 论文报告的结果只针对稠密的小 attention 应用。**MoE 路径是随代码一起发布但既无文档、又无 CI 覆盖的分支。**

### 1.4 最可能的崩溃机理（定位到具体代码，但未做最终确认）

`moe_linear_mi300.cuh:98-115`：

```cpp
int const num_activated_experts = d_mask[NUM_EXPERTS];
...
for (int ae_idx = actual_expert_offset; ae_idx < num_activated_experts; ae_idx += EXPERT_STRIDE) {
    int32_t expert_id = d_mask[ae_idx];
    bf16 const *expert_weight = d_weight + (int64_t)expert_id * OUTPUT_STRIDE * REDUCTION_SIZE;
```

`d_mask` 就是 `moe_mask`，长度 `NUM_EXPERTS + 1 = 129`。如果 `num_activated_experts`（存在 `d_mask[128]`，由路由 kernel 写入）是**异常大的值或未初始化**，这个循环就会读 `d_mask[ae_idx]`（越界）拿到垃圾 `expert_id`，再拿它去索引专家权重 → 偏移量爆炸 → **非法访存**。这与观测到的现象（任务派发正常、执行期越界）吻合。

路由 kernel 里确实有一处**同数组原地压缩的数据竞争**（`moe_topk_softmax_mi300.cuh` 末尾）：

```cpp
for (int expert = start_expert + threadIdx.x; expert < end_expert; expert += blockDim.x) {
    int const local_expert = expert - start_expert;
    int const mark = active_expert_ids[local_expert];      // 读 [0..127]
    if (mark >= 0) {
        int const pos = atomicAdd(active_expert_ids + NUM_EXPERTS, 1);
        active_expert_ids[pos] = expert;                    // 写 [0..127]，同一个数组
    }
}
```

读和写落在**同一个数组**上，且没有同步：先完成的线程会覆盖后面线程即将读取的槽位，导致激活专家列表被重复填充或写入不该写入的项。计数 `d_mask[128]` 因此可能与列表内容不一致。

**这只是一个基于代码的强假设，本轮没有做最终确认**（确认需要在 kernel 内插桩或逐任务二分）。

## 2. 结构性归因：几何与数据基数错配（已量化）

崩溃之外，即使跑起来，这套实现在几何上也是错配的。这是本轮**不受崩溃影响**的部分，因为它由代码结构决定，可用路由统计独立量化。

### 2.1 代码结构：稠密 M 行 GEMM + 仅 epilogue 跳过

`gang_moe_linear_mi300.cuh:120-190`（`moe_linear_mi300.cuh` 同构）：

```cpp
// Input A: offset to M-tile
index_t m_offset = m_tile * MPerBlock;
bf16 const *a_base = d_input + (size_t)m_offset * REDUCTION_SIZE;
...
Pipeline pipeline;
auto c_block_tile = pipeline(a_tile_window, b_tile_window, NumLoopK, smem);
...
// ---- Epilogue: scatter-write results using routing indices ----
int const route_val = expert_routing[global_m];
if (route_val != 0) {          // <-- 只在这里跳过
    ... scatter write ...
}
```

即：**GEMM 对全部 `BATCH_SIZE` 行照算，A 矩阵也照样读，只有写回时按路由跳过。** 每个被激活的专家都要付一次完整的 M=BATCH_SIZE 的代价。

### 2.2 真机路由统计（`moe_routing_stats.py`，Qwen3-30B-A3B）

在 PyTorch 侧对同一套权重挂 hook 统计 top-k 路由（路由是隐状态的确定函数，两边输入相同则结果相同）。用 32 条**差异化**提示词，取每条序列真实末位 token 的路由：

| batch | 激活专家数（均值/区间） | 每激活专家 token 数 | 行利用率（含 16 行 tile 取整） | 浪费因子 |
|:---:|:---:|:---:|:---:|:---:|
| **1** | 8（恒为 topk） | **1.0** | **6.25%** | **16.0×** |
| **32** | 26.5（13–45） | 10.67 | 33.3% | 3.31× |

全序列口径（2048 次分配）作为路由分布的整体刻画：**平均 101.5/128（79%）个专家被激活，头部专家占全部分配的 10.75%**——路由是**明显偏斜**的。

### 2.3 三点解读

**① 计划的 P1 假设成立，而且在低 batch 更严重。**
计划担心"`MPerBlock` 是编译期 16，而每专家 token 数是运行期数据相关量"。实测 bs=1 时每专家恰好 **1 个 token**，却要算 16 行 → **6.25% 填充，16× 浪费**。这是整个 Part B 最干净的一个数字。

**② 浪费随 batch 增大而缓解，但不是因为几何变好。**
bs=32 时浪费降到 3.31×，主要来自"激活专家数从 8 涨到 26.5、每专家 token 数涨到 10.67"，仍然是 16 行 tile 装 10.67 个 token。

**③ 我此前用"均匀路由"算出的 13.9× 是错的，这里更正。**
均匀假设下 32×8=256 次分配会打在 110.8 个不同专家上，得到 7.2% 利用率。**实测只有 26.5 个**，因为路由偏斜（头部专家占 10.75%）。偏斜实际上**减少**了浪费（更少的专家被触及、每个专家更满）。**以实测的 3.31× 为准，不要用均匀假设。**

> 一个测量上的坑：如果 32 条提示词内容相近，它们的末位 token 会相同，路由退化成全部落在同 8 个专家上（我第一版就是这样，测出 `num_activated=8`、利用率 100% 的假象）。必须用差异化序列。

## 3. Roofline：这些浪费付得起吗？

**这是决定"该往哪儿优化"的关键，不能只看浪费倍数。**

Qwen3-30B-A3B：hidden=2048、moe_inter=768、128 专家、topk=8、48 层、bf16。

| 量 | 值 |
|---|---|
| 每专家权重 W13 | 6.29 MB |
| 每专家权重 W_down | 3.15 MB |
| **每专家合计** | **9.44 MB** |
| 全部专家 × 全部层 | 58.0 GB |

bs=32 实测（26.5 个激活专家）：

| 量 | 值 |
|---|---|
| 每次迭代 MoE 权重访存 | 12.0 GB（占全体专家权重的 21%） |
| **访存下限**（3.7 TB/s） | **3.24 ms/iter = 0.10 ms/token** |
| MoE GEMM 实际工作量 | 0.38 TFLOP/iter → 0.29 ms at peak |
| 算术强度 | **32 FLOP/byte** vs 机器 ridge **353 FLOP/byte** |
| 结论 | **强访存受限**；浪费的算力（0.29 ms）**大半藏在 3.24 ms 的访存后面** |

**所以：**

- 按"被浪费的行"去优化（比如改成按专家 gather token），**收益上限很低**，因为那部分算力本来就不在关键路径上。
- 真正决定 decode MoE 性能的是**权重访存**：每次迭代要读 12 GB，无可避免。
- 而"读 12 GB"这件事本身**是路由决定的，不是 kernel 决定的**——26.5 个专家里有 token 就得读。**这是 MoE 的固有性质，不是 Fleet 的缺陷。**

**由此得到一个略微反直觉但重要的判断：Fleet 的 MoE 在"权重访存"这一维度上并不 naive**（每个激活专家只读一次，没有冗余读）。它 naive 的地方是：(a) 对每个专家按 BATCH_SIZE 而非实际 token 数做 GEMM；(b) 由此产生的激活值访存与算力浪费——而在 bs≥32 时后者大部分被隐藏。

**注意一个未完成的关键对照：因为 MoE 跑不起来，本轮没有拿到任何 Fleet MoE 的实测 ms/token，所以上面只能给"下限"，无法算"实测/下限"的达标率。** 这是 Part B 最大的缺口。

## 4. 另一处独立缺陷：路由 kernel 只覆盖 16 行

`moe_topk_softmax_mi300.cuh` 的行覆盖是**编译期固定**的：

```cpp
static constexpr int ELTS_PER_WARP  = MI300_WARP_SIZE * VPT;   // 64 * 8 = 512
static constexpr int ROWS_PER_WARP  = ELTS_PER_WARP / ELTS_PER_ROW;  // 512/128 = 4
int const warp_base_row = warp_idx * ROWS_PER_WARP;
```

`WARPS_PER_CTA=4`（`task_register.cc` 实例化为 `topk_softmax_mi300_task_impl<hip_bfloat16, 8, num_experts, 4, 16>`），256 线程 = 4 个 wavefront × 每个覆盖 4 行 = **一个 block 只覆盖 16 行**。

而 demo 里这个 task 的 grid 是 **`(1, 1, 1)`**（`demo_30B_A3B.py:698`）：

```python
mpk.moe_topk_softmax_routing_layer(
    input=moe_gate_out, output=(...), grid_dim=(1, 1, 1), block_dim=(256, 1, 1))
```

**所以无论 batch 多大，只有前 16 行会得到路由结果**，第 17 行往后 `routing_indices` 保持初始化的 0（= 无专家），`moe_topk_weight` 保持未初始化。这是一个**静默的正确性缺陷**（不崩溃，只是结果错），且与 §1 的崩溃是两回事。

对 Qwen3-30B-A3B 的 128 专家、`ELTS_PER_ROW=128`、`VPT=8` 这组参数，`THREADS_PER_ROW = 128/8 = 16`，正好把 64 线程的 wavefront 分成 4 组——也就是说**这套模板参数是为 128 专家 + 单 block 覆盖 16 行专门配的**，batch>16 从未被覆盖。

## 5. 对计划算术的两处修正

**① 每专家权重大小。** 计划 §3.2 写"专家权重 3.15 MB/个"。实际 W13 = 2×768×2048×2B = **6.29 MB**，W_down = 768×2048×2B = **3.15 MB**，合计 **9.44 MB**。计划把 W13 的**元素数**当成了字节数（少算 2 倍），且漏了 W_down。

**② MoE 浪费倍数。** 计划 §0.1 推测"约 8× 的浪费"。实际应以 `激活专家数 / topk` 与 16 行 tile 填充率两个口径分别表述：实测 bs=1 为 **16×**（tile 口径）、bs=32 为 **3.31×**。均匀路由假设给出的 13.9× 不成立（路由偏斜）。

计划里"Mixtral 规模下 B=8 时每专家平均只有 2 个 token"这半句方向是对的，但按 Mixtral 的 8 专家/topk=2 算，`num_activated/topk` 最多 4×。

## 6. 研究空间判断

**结论：空间很大，但不是"把浪费的行抠掉"那种空间。**

值得做的方向（按我判断的价值排序）：

1. **先把 MoE 路径修到能跑。** 这是前提。没有实测数，后面所有讨论都停在纸面。最可能的着手点就是 §1.4 的原地压缩竞争 + 内存序。
2. **token-major / gather 式的 MoE 组织。** 现在每个专家重读 N 的权重来服务少量 token；改成按 token 聚合、或按 (expert, token-block) 紧凑排布，能同时省掉 16 行 tile 的填充浪费和 A 矩阵的重复读。**但按 §3 的 roofline，这会省的是算力和激活访存，不是权重访存——所以在 bs=32 收益有限，在 bs=1 收益更小（权重访存占比更高）。** 这条路的真正价值在于**为更大 batch 腾出算力余量**。
3. **降低每步的权重访存量** —— 这才是关键路径。可行方向：跨 XCD 的专家亲和性调度（让热门专家固定落在同一 XCD，提高 L2 命中）、权重量化（bf16→fp8 直接把 12 GB 砍半）、以及**把"哪些专家被激活"的预测/预取与计算重叠**。
4. **跨 XCD 的 L2 分片复用**：计划 §3.2 已经注意到 Qwen3-30B-A3B 是"极小专家"（每专家切片 0.39 MB，远小于 4 MB L2），**它跑得好不能推出 MoE gang 成立**。但这轮连单模型都没跑起来，Mixtral 级对照无法进行。
5. **注意：Fleet 的 gang 机制在 MoE 上的适用性本身就是个开放问题。** 稠密路径的收益来自"同一 XCD 的 worker 共享 L2 里的权重"；MoE 每个专家权重 9.44 MB、每 XCD 要处理约 26.5/8 ≈ 3.3 个专家 ≈ 31 MB，**远超 4 MB L2**。也就是说，gang 的 L2 复用前提在 MoE 上是否还成立，需要在修好之后实测 B4 才能判断。

**一句话给研究定位**：这不是"Fleet 的 MoE 慢了 3 倍"的问题，而是"**这套框架的 MoE 支持尚未完成，而 MoE decode 的性能天花板由权重访存决定，现有 gang/L2 复用机制对它是否适用还没有任何真机证据**"。这恰好是一个空白且值得做的方向。
