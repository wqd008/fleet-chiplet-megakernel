## 0. 当前结论

**MoE 路径从"完全不执行"推进到"bs=1 非 gang 能端到端跑完"**（16.995 ms/token）。共修掉 **4 个真实缺陷**，其中 2 个是纯粹的 MI300X 移植问题。

## 1. 修掉的 4 个缺陷

### 1.1 lm_head / argmax 的 grid 按 worker 数分配（**MI300X 专属杀手**）

`demo_30B_A3B.py` 把 lm_head 和 argmax 的 grid 直接设成 `mpk.num_workers`，而 padding 后的 vocab = 153600 要按 worker 数切分：

| 平台 | CU | scheduler | **worker** | `153600 % worker` | |
|---|---|---|---|---|---|
| MI350 | 248 | 8 | **240** | **0** | ✅ |
| **MI300X** | 304 | 8 | **296** | **272** | ❌ **最后一个分片越界读 lm_head** |

稠密 demo 早就有保护（`demo.py:511`：`argmax_tasks = num_workers if vocab % num_workers == 0 else 240`），MoE demo 没有。

**修复**：照搬该表达式，并把三处 `mpk.num_workers` 换成 `argmax_tasks`（`argmax_part_value`/`argmax_part_index` 的 dims、lm_head 的 `grid_dim`、`argmax_partial_grid_dim`）。

**效果**：megakernel 开始执行，不再是第一次迭代就 `HIP error: an illegal memory access`。

> 这解释了全部原始现象：与 batch 无关、与 gang 无关、第一次迭代就崩、稠密路径却完全正常。

### 1.2 `use_cutlass_kernel` 没有在 ROCm 上强制关闭（**MI300X 专属**）

`demo/qwen3/demo.py:156`：

```python
# This also fixes grid_for_rmsnorm_linear_layer to return size//64
if getattr(torch.version, "hip", None):
    args.use_cutlass_kernel = False
```

注释明确写了 CUTLASS 需要 CUDA tensor core，且该开关**同时决定 `grid_for_rmsnorm_linear_layer` 的返回值**。**MoE demo 完全没有这段。** 实测它以 `use_cutlass_kernel=True` 在 MI300X 上运行。

**修复**：在 `args = parser.parse_args()` 之后加入同样的两行。

### 1.3 路由 kernel 单 block 只覆盖 16 行

`moe_topk_softmax_mi300.cuh` 的行覆盖是编译期固定的：
`ROWS_PER_WARP = (64×8)/128 = 4`，`WARPS_PER_CTA = 4` → 每 block 仅 16 行；而 demo 用 `grid_dim=(1,1,1)` 启动 → **batch > 16 的行永远拿不到路由**。

**修复**：`WARPS_PER_CTA` 4 → 16（`src/kernel/task_register.cc`），demo 的 `block_dim` 256 → 1024（16 warp × 64 线程），单 block 覆盖 64 行。

### 1.4 gate 的 grid 与 block 不对齐稠密 demo

MoE gate 原为 `grid_dim=(1,1,1), block_dim=(256,1,1)`。稠密 demo 里所有 `linear_layer` 都是 **grid = 输出维度 // 64、block_dim = 128**（`grid_for_rmsnorm_linear_layer` 在不启用 cutlass 时即 `size//64`：w_qkv 6144→96、gateup 24576→384）。

**修复**：改为 `grid_dim=(num_experts // 64, 1, 1), block_dim=(128, 1, 1)`。

（单独看这一条并未消除 NaN，但它是与已验证可用的稠密路径对齐的必要一步。）

## 3. 剩余故障的定位（已很具体，但未解决）

用逐层插桩（`MPK_DEBUG_MOE_MASK=1`）得到的证据链：

**bs=32 时：**

1. 路由 kernel 看到的 gate 输出全是 NaN：
   `[TOPK_DBG] gate_in[0][0..7]: -nan -nan ...`
   → 所有 logits 相等 → top-k 平局判据退化 → **8 个槽位全投专家 0** → 实测 `nact=1, mask: 0 -1 -1 ...`、`route0: 8 8 8 8 8 8 8 8`。
2. gate GEMM 本身正常：`[LIN_DBG] B=32 K=2048 OSIZE=64 OSTRIDE=128 nat=32 | w0=0.015442`（权重正常、形状参数全部正确），**但 `in0=-nan`**。
3. 往上游一层：rmsnorm 的**输入完全干净**：
   `[RMS_DBG] in[0]=-0.001007 in[1]=-0.038818 in[8]=0.012573 in[64]=-0.015076 in[1024]=0.007935 in[2047]=0.010986`
4. 而 rmsnorm 的输出缓冲区在写入前是 0.0（`out0_pre=0.000000`），gate 却在缓冲基址读到 NaN。
5. 指针核对：gate 的 `in_ptr` 就是 `rmsnorm_out` 的基址，rmsnorm 各 block 的 `out_ptr` 落在同一缓冲区内 —— **指针自洽**。

**推论**：gate 读到的是 rmsnorm **尚未写入**的内容（未初始化显存），即 **rmsnorm 任务与 gate 任务之间缺少有效的完成序**。已验证**不是**以下几种：

- ✗ 不是 NT store 的可见性问题（把 rmsnorm 的 non-temporal store 换成普通 store，NaN 不变）；
- ✗ 不是 topk kernel 清零自己输入导致的写-写冲突（禁用那段落清零，NaN 不变）；
- ✗ 不是 gate 的 grid/block；
- ✗ 不是 `moe_gate_out` 未初始化（改成 host 侧零初始化张量后仍是 NaN）；
- ✗ 不是权重问题（`w0` 正常）。

**bs=1 时同样的插桩显示 gate logits 是真实数值**（`-4.0625 -3.859 ...`），说明该排序问题只在 bs=32 出现。

## 5. 下一步

1. **查 MPK 的任务完成序**：为什么 bs=32 时 gate 会读到尚未写入的 `rmsnorm_out`，而 bs=1 不会。这是当前唯一的拦路石。切入点：`rmsnorm_out` 是**单个张量被 48 层共用**，写-写与读-写依赖都可能因此退化；可试每层独立缓冲，或用 `MPK_ENABLE_DEVICE_TASK_TIMING` / profiler 看实际任务序。
2. 修好后**先做正确性验证**（与 PyTorch 路径比对 token），再做性能。
3. 然后才是 B4 / B3 / B5。

## 6. 对研究判断的影响

归因文档 §6 的判断不变，且证据进一步加固：

- "MoE 未完成" 现在是 **6 个独立缺陷**：lm_head grid、cutlass 开关、路由行覆盖、gate grid、gate NaN、以及 bs=1 输出非文本。分布在 demo 脚本 / C++ 注册层 / device kernel 三处。
- **其中 2 个（lm_head grid、cutlass 开关）是纯粹的 MI350→MI300X 移植缺失** —— 这本身就说明这条路径只在 MI350 上被跑过，且没有 CI 保护。
- "性能天花板由权重访存决定" 不变。
- 新增：**bs=1 的 17 ms/token 与稠密 Qwen3-8B 的 15.5 ms/token 量级相当**，而 30B-A3B 的激活参数量远小于 8B 稠密 —— 若最终确认，这本身就是一个"MoE 实现存在显著优化空间"的强信号。但这需要在输出正确之后再谈。
