## 0. 一句话摘要

**Part A 已完成；Part B 已完成归因（结论是 MoE 路径无法运行）。**

Fleet 可以在 MI300X 上跑通，但**需要修正五处环境问题**，其中最关键的是必须把 `deps/composable_kernel` 固定到某个特定提交。

### 最关心的两个问题，直接回答

**问题一：参数搜索是否有较好的性能提升（⇒ 其他算子自动生成是否有意义）？**

**有，而且这个结论比"快几个百分点"更重要。** bs=32 下最优配置比 Fleet 硬编码默认快 **8%**（35.711 vs 38.893），相对噪声下限（中位数 2.6%）站得住。但真正支持"自动生成有意义"的是另外两条：

- **最优参数随 batch 移动**：bs=1 与 bs=32 的排名**完全相反**（bs=1 时默认反而快 9.1%）。单一常数不可能同时最优。
- **最优参数随硬件移动**：MI350（每 XCD 约 30 worker）上调好的几何，在 MI300X（每 XCD **37** worker）上不是最优，Fleet 出厂默认**甚至比不用 gang 还慢 2.6%**。

**⇒ 也就是说，"手工调好的常数不可迁移"这件事有真机证据支持，这正是自动生成/自动调优的价值所在。** 注意：8% 是端到端数字；因为 attention 占了 bs=32 迭代的约 66%，换算到 linear 部分约 25%。详见 §5 与 §6。

**问题二：MoE 算子用这套框架性能是不是很 naive？还有优化空间吗？**

**是，而且比 naive 更严重——它跑不起来。** 详见 `docs/results/2026-11-16-PartB-MoE归因.md`。三句话版本：

- MoE 路径在 bs=1/8/16/32、gang/非 gang 共 6 种组合下**全部崩溃**（非法访存），且无文档、无 CI 覆盖；
- 代码结构上确实错配：每个激活专家做 M=BATCH_SIZE 的稠密 GEMM，行利用率 bs=1 仅 **6.25%（16× 浪费）**、bs=32 为 33.3%；
- 但 roofline 显示它**强访存受限**（算术强度 32 vs ridge 353），浪费的算力大半被隐藏——**所以优化空间在权重访存与调度，不在"抠掉浪费的行"**。

## 1. 环境实际情况（与计划假设的差异）

计划 §1 假定镜像基本就绪，只需要设置 `AMDGPU_TARGETS`。实际情况不是。

| 项目 | 计划假设 | **实测** |
|---|---|---|
| GPU | MI300X | MI300X **VF**（虚拟功能），`gfx942` |
| CU 数 | 304 | **304** ✓ |
| 显存 | 192 GB | **191.7 GB** ✓ |
| ROCm | 7.2.4 | **7.14.1**（`/opt/rocm/core-7.14`，clang 23） |
| PyTorch | 已装 2.10.0 | **完全没装**——自行安装 `2.10.0+rocm7.0` |

**每 XCD 的 worker 数（计划明确要求记录）：**

```
sm_cnt:  304
AMD config: workers=296, schedulers=8, physical_blocks=304, CUs=304
```

即 304 CU / 8 XCD = 每 XCD 38 个 CU，其中 1 个是 scheduler，**剩 296 个 worker = 每 XCD 37 个**（编译参数 `-DMAX_WORKER_PER_SCHEDULER=38`）。MI350 是 248 CU / 8 XCD = 每 XCD 31 个，约 30 个 worker。**所以 MI300X 每个 XCD 多了约 23% 的 worker 争抢同一块 4 MB L2**——这正好是 Fleet 几何参数所调度的资源，也是 MI350 上调好的常数无法直接迁移的合理解释（见 §4）。

## 3. composable_kernel 的版本（最不显然的一处）

Fleet 的 MI300 kernel 会 include `deps/composable_kernel/include` 下的 `ck_tile` 头文件，源码注释写着"必须排在系统 CK 之前"。这条很关键：**ROCm 7.14 自带的系统 CK 与 Fleet 手写的 policy 不兼容**，报错是 `gemm_pipeline_ag_bg_cr_base.hpp` 要求 `Policy::is_a_load_tr`、`MakeADramTensorView` 等 Fleet 没有定义的成员。

用 GitHub API 逐步二分定位（`find_ck_commit.py`）：

| CK 参考点 | FMHA `TileFmhaFwdSplitKVTraits` | GEMM pipeline 是否要求 `Policy::is_a_load_tr` | 结论 |
|---|---|---|---|
| rocm-7.0.0 / 7.0.2 | 13 参数，无 `kHasSink` | 否 | 太旧（FMHA 参数个数不符） |
| rocm-7.1.x / 7.2.x | 13 参数 | 否 | 同上 |
| therock-7.9.0 / 7.10 | 13 参数 | 否 | 同上 |
| **`ac18460782fa`**（develop） | **14 参数，有 `kHasSink`** | **否** | **✓ 匹配** |
| 下一个 develop 提交 `717f2efe` | 14 | **是** | 太新 |
| 系统 ROCm 7.14 | 14 | **是** | 太新 |

Fleet 调用 `TileFmhaFwdSplitKVTraits` 时传了 **14 个模板参数**（第 14 个是 `kHasSink`），把它锁定在"sink attention 已加入、但 pipeline policy 重构尚未发生"的 develop 快照上。`ac18460782fa` 是同时满足两个约束的最新提交，因此固定于此（sparse 拉取，只取 `include/`，114 MB）。

> **后果：`deps/composable_kernel` 必须停在这个提交。** 升级它、或让 `/opt/rocm/include` 抢占 include 顺序，构建就会失败。

## 4. 唯一剩下的 MI350 专属问题：`USE_CK_FMHA=1`

CK 固定后，构建只剩 **两个** 错误，都在同一个文件
`include/mirage/persistent_kernel/tasks/mi300/paged_attention_decode_minimal_mi300.cuh`：

```
:27  __builtin_amdgcn_mfma_f32_16x16x32_f16   needs target feature gfx950-insts
:47  __builtin_amdgcn_ds_read_tr16_b64_v4f16  needs target feature gfx950-insts
```

两者都经过编译实测确认是 gfx950 专属：16x16x16 的 f16 MFMA 在 gfx942 上可以编译，**16x16x32 的形式不行**；而 transposed LDS 读（`ds_read_tr`）是 CDNA4 才有的指令，**gfx942 上根本不存在**。

这个文件是 `seqlen_q == 1` 的 **decode attention**，由 `paged_attention_ck_fmha_split_kv_mi300.cuh:594` 调度，**位于 decode 关键路径上**，不是死代码。文件名叫 `_mi300`，内容是 MI350。

全仓扫描确认：**只有这一个文件**使用了 gfx950 专属 intrinsic，其余（`mfma_f32_16x16x16bf16_1k`、`s_memrealtime`、`readfirstlane`、`rcpf`、`fence`）在 gfx942 上都安全。

### 采取的方案：不改 kernel 代码，改用 `USE_CK_FMHA=0`

`USE_CK_FMHA=0` 会通过 `tasks/mi300/task_header.cuh:34` 的 `MPK_USE_CK_FMHA` 开关把这个文件排除掉。已验证端到端可用。

理由与边界：
- Fleet 的 gang **linear** kernel（A 部分参数搜索的真正对象 `GANG_TILE_N`/`GANG_M_TILES`/`GANG_WGM`）完全不受影响，全部启用。变化的只有 attention 后端。
- 所有配置用的是同一个 attention 后端，因此 gang-非gang、参数-参数的**相对比较仍然内部有效**。
- 计划 §3.4 本来就声明绝对时间不可与 README 的 MI350 比较，这一点没有额外损失。
- **代价：** attention 是两臂共有的每次迭代开销。它占的比例越大，gang 的相对收益被稀释得越厉害。另外它还会挡住 bs=64（见 §5.3）。

### 另一条路：改路由，但实测更慢，因此没有采用

在分支 `mi300x-adaptation` 上实现了可移植性修复，让 `USE_CK_FMHA=1` 至少能编译：

- `tasks/mi300/task_header.cuh` —— 只在 `#if defined(__gfx950__)` 时 include 那个 MI350 文件。
- `paged_attention_ck_fmha_split_kv_mi300.cuh` —— 非 gfx950 时，`seqlen_q == 1` 改走 `paged_attention_ck_fmha_prefill`（它把 `seqlen_q` 当运行期参数收）。

两处改动都在 `#ifdef MPK_USE_CK_FMHA` / `#if defined(__gfx950__)` 之内，**`USE_CK_FMHA=0` 时完全惰性**。这一点既有静态检查、也有实测印证（A0/A1 早于改动、A2–A5 晚于改动，同一配置跨改动前后在噪声内一致：`A0_tile64` 38.925 → `A2_tile64_wgm0` 38.893；`A1_gang_default` 39.757 → `A4_bs32_default` 38.313）。

实测（bs=1，同提示词，同 gang 配置）：

| 配置 | ms/token |
|---|---|
| `USE_CK_FMHA=0`（本报告全部数据所用） | **10.207** |
| `USE_CK_FMHA=1`（MI350 decode kernel 被 CK prefill pipeline 顶替） | 15.390 |

kernel 每轮会打印 `[FWD_PASS] iter=N time_ms=...`，可以直接看出随上下文增长的开销：

- `USE_CK_FMHA=0`：**平坦** —— iter 900 约 10.05 ms，iter 1100 约 10.13 ms。
- `USE_CK_FMHA=1`：**随上下文上升** —— iter 1 约 10.0 ms，iter 1000 约 18.9 ms，iter 1100 约 20.7 ms。

替代方案用 prefill 形状的 kernel 每步重算整个 KV 范围，所以随上下文线性增长；Fleet 原意中专门为 decode 写的 kernel 不会这样。**因此这个替换是劣化，不是等价交换。**

**结论：采用 `USE_CK_FMHA=0`。** 它不需要改任何 kernel 代码（满足计划 §0.3 的硬约束），是目前两种可选方案里更快的一种，且 bs=1 下 attention 开销与上下文无关。真正的修法——把 `paged_attention_minimal_decode` 移植到 gfx942——仍然未做，**这是目前价值最高的后续工作**。

## 5. Part A 结果

模型 Qwen3-8B bf16，单卡，`USE_CK_FMHA=0 USE_FUSED_SILU=1 GANG_M_TILES_GATEUP=1`，提示词与生成长度按计划固定（94 token 提示词，1024 decode token）。**每次改参数都删了 `permanent_output_dir/` 重新编译。**

### 5.1 先确定噪声（因为后面所有判断都依赖它）

把同一配置的多次运行（显式的 repeat，以及 A0/A1/A2 中重叠的配置）合并统计，13 个被重复测量过的配置给出：

> **运行间波动：中位数 2.6%，最差 6.5%**

> 早期基于 3 个样本估计的"约 2%"偏乐观，已作废。**低于约 2% 的差异在现有重复次数下不可分辨；单样本下低于 6.5% 的差异不能断言为真。**

这是本文最重要的一条背景：它正是为什么 A0 第一遍看起来是 `tile_n=128` 干净利落的 9% 领先，而合并数据后回落到约 6–8%。

另外，指标对上下文长度敏感（attention 开销随 KV 增长），所以只能用同一会话内的比较。

### 5.2 主扫描：bs=32，`m_tiles` 取默认（`bs//16` = 2）

合并中位数，`n` 是该配置的运行次数。

| tile_n | wgm=0 | wgm=1 | wgm=2 | wgm=4 | 行最优 |
|:---:|:---:|:---:|:---:|:---:|:---:|
| 64（Fleet 默认） | 38.893 (n=5) | 39.080 (n=2) | 38.364 (n=2) | 37.389 (n=2) | 37.389 |
| **128** | 37.505 (n=3) | **36.071** (n=2) | **35.711** (n=2) | **36.374** (n=2) | **35.711** |
| 256 | 40.290 (n=3) | 38.721 (n=2) | 39.949 (n=2) | 39.597 (n=2) | 38.721 |
| **不用 gang（MPK 基线）** | 37.913 (n=1) | — | — | — | 37.913 |

**结论一：`tile_n = 128` 比 Fleet 硬编码的 64 快约 6–8%。**
证据比单个中位数更强：它在 **wgm 的四个取值上全部胜出**（4/4 配对比较），符号检验 p ≈ 0.06（双侧），幅度也在最差噪声之上。Fleet 默认（64, wgm=0）38.893 vs（128, wgm=2）35.711，**快 8.2%**。

`tile_n = 256` 在每个 wgm 下都比默认差——**说明这个空间确实非单调，不是"越大越好"**，128 是一个真实的内部最优，不是边界效应。

**结论二：`GANG_WGM` 不是白送的收益，但一旦 `tile_n` 选对，`wgm = 0` 看起来是个错误的默认值。**
在 tile_n=128 下，所有非零 wgm（35.71 / 36.07 / 36.37）都优于 wgm=0（37.51），差约 3–5%。但在 tile_n=64 和 256 下 wgm 的排序并不一致（64 的最优是 wgm=4，256 的最优是 wgm=1），这正是噪声的样子。**因此这条只能算"提示性结论"，尚不能断言**，需要更多重复。不过它确实指向计划正确识别出的那个从未被调过的量——源码里 `GANG_WGM` 恒为 0。

**结论三：Fleet 出厂默认相对"不用 gang"没有任何收益。**
默认 gang 38.893 vs 不用 gang 37.913，默认 gang 反而**慢 2.6%**。这与 README 在 MI350 上报告的 bs=32 时 1.23× 加速矛盾。可能的机制见 §1：MI300X 每 XCD 37 个 worker，MI350 约 30 个，**多出约 23% 的消费者共享同一块 4 MB L2 slice**，而 gang 几何调度的正是这块资源。为 30 个 worker 调好的几何，对 37 个未必合适。

**调好的 gang 配置确实能超过基线**：35.711 vs 37.913，**快 5.8%**。

### 5.3 A4：batch 延展

| bs | Fleet 默认（tile_n=64, wgm=0） | 调优（tile_n=128, wgm=2） | 胜者 |
|:---:|:---:|:---:|:---:|
| 1 | **10.291** | 11.227 | **默认，快 9.1%** |
| 32 | 38.313 | **36.334** | **调优，快 5.3%** |
| 64 | **崩溃** | **崩溃** | — |

**最优参数随 batch 移动，这是 Part A 最重要的结果。** 在 bs=32 最优的几何，在 bs=1 反而比 Fleet 默认**慢 9.1%**，反之亦然。bs=1 时生成受权重带宽限制，较窄的 `tile_n` 更优；bs=32 时 M 方向的工作量足够摊薄宽 tile 的开销。**Fleet 对两者只发一个常数。**

（bs=1 那行是手工跑的：driver 无法表达"按 batch 取不同的 `m_tiles`"，而 `m_tiles=2` 在 bs=1 非法。用合法几何 `GANG_M_TILES_OVERRIDE=1`。见 `results.tsv` 的 `A4_bs1_best_mt1` 行与 `logs/manual_bs1_best.log`。）

#### bs=64 完全跑不起来，而且是我们自己配置的锅

`A4_bs64_*` 是断言崩溃（不是超时）：

```
src/threadblock/graph.cc:45: Assertion `grid_dim.x * grid_dim.y * grid_dim.z <=
MAX_NUM_THREADBLOCKS_PER_KERNEL' failed.
```

`MAX_NUM_THREADBLOCKS_PER_KERNEL = 4096`（`include/mirage/config.h:39`），触发它的层已精确定位——`demo.py:778` 的 split-KV attention 层：

```python
grid_dim=(mpk.max_num_batched_requests, num_local_kv_heads, num_kv_cache_chunks)
```

其中 `num_local_kv_heads = 8`（Qwen3-8B），`num_kv_cache_chunks = ceil(1200/128) = 10`：

| bs | grid | 乘积 | 对 4096 |
|:---:|---|---|---|
| 32 | (32, 8, 10) | 2560 | 通过 |
| 64 | (64, 8, 10) | **5120** | **失败** |

已验证与 gang 无关：bs=64 下 `USE_GANG=0` 同样崩溃。这是 `USE_CK_FMHA=0` 这条 attention 路径的性质——README 用的 `USE_CK_FMHA=1` 路径 grid 是 `(bs, 8, CK_FMHA_CHUNKS=1)`，bs=64 时只有 512，所以 MI350 和论文里 bs=64 能跑。**这是 §4 中 `USE_CK_FMHA=0` 替换的代价，也是想要真正移植 gfx942 decode attention 的第二个独立理由。**

可用的绕法（本次都没用）：把 `--max-seq-length` 降到 ≤1024（chunks ≤ 8 → grid 恰好 4096），或改用 CK FMHA 路径。两者都改变工作负载，所以 A4 的 bs=64 一列留空，而不是填一个不可比的数。

#### `m_tiles` 必须整除 batch

`A4_bs1_best` 失败于 `assert batch 1 must be divisible by m_tiles 2`（`persistent_kernel.py:1599`）——计划所说的约束，得到确认。**把它作为失败样本记录是刻意设计的**：这是关于参数空间真实自由度的证据，不是 driver 的 bug。

### 5.4 A5：对照组

| 对照组 | ms/token | 匹配基准 | 预期 | 裁决 |
|---|---|---|---|---|
| `USE_GANG_N_TILE=1`（阴性） | 36.387 | 35.711（`tile_n=128,wgm=2,m_tiles=bs//16`） | 不应有收益 | ✅ 无收益——反而慢 1.9% |
| `GANG_M_TILES_GATEUP=4`（阳性） | 36.277 | 36.909（`m_tiles=2, wgm=2, GATEUP=1`） | 可能有收益 | ❌ 无可分辨收益——快 1.7%，在中位噪声 2.6% 之内 |

**阴性对照是这里最有价值的一次测量。** 计划指出：如果 `USE_GANG_N_TILE=1` 也变快，那么整个 A 部分结论就必须重新解释为"任何 gang 变体都快"，而不是"M 轴上的权重复用"。它没有变快，且代价与 M-tiling 变体接近（36.387 vs 35.711，都远离 38.9 的默认值）。**因此 A 部分的结论建立在预期机制上，而不是假象上。**

阳性对照没有显示收益，按实测报告。这不矛盾——计划预期有收益的依据是另一个模型上的先例，而在 bs=32 且 `m_tiles` 已经是 2 的情况下，可能本来就没剩多少空间。

### 5.5 正确性验证（有效性闸门）

在有数据可信之前先验证输出正确：

- MPK 与 PyTorch 贪心参考在**前 47 个 token 完全一致**，之后分歧——这是 bf16 logits 打平的典型特征，不是 bug。
- MPK 比 torch eager 快 2.6×（11.0 vs 29.1 ms/token），说明 megakernel 确实在高效工作。
- bs=32 下 32 个 batch 的输出彼此完全一致（各 1200 token）。

### 5.6 回答计划 §4.3 的四个问题（Part A 部分）

**问题 1：静态参数搜索的空间有多大？**
bs=32 下约 8%（35.711 vs 38.893），**超出噪声，但幅度不大，而且只因为有重复测量才站得住**。换算到 linear 部分约 25%（见 §6）。

**问题 2：最优参数是否随 batch / 模型移动？**
**随 batch：是。** bs=1 与 bs=32 的最优解互相矛盾，两个方向都超出噪声。**随硬件：更是。** 在 MI350（30 worker/XCD）上调好的几何，在 MI300X（37 worker/XCD）上不是最优，Fleet 的出厂默认甚至不如关掉 gang。这就是"必须搜索而非常数"的直接证据。

**问题 3、4（MoE 相关）：本轮未做**，见 §8。

## 6. 一个影响结论解读的限制：attention 稀释

`demo/qwen3/demo.py --linear-only` 只注册 linear 任务（跳过 attention 和 silu）。用同一配置跑它和完整流程，可以分离出非线性部分。Qwen3-8B，bs=32，`USE_GANG=1 USE_CK_FMHA=0 USE_FUSED_SILU=1 GANG_M_TILES_GATEUP=1 GANG_TILE_N=64`：

| 运行 | ms/token |
|---|---|
| 完整（开 attention） | 38.925 |
| `--linear-only` | 13.263 |

    非线性占比 = (38.925 - 13.263) / 38.925 = 65.9%

**bs=32 下一次 decode 迭代约三分之二是 attention**，只有约三分之一是参数搜索真正扰动的 gang linear 工作。所以本文所有差异相对其"对 linear 部分的影响"都被稀释了约 3 倍。`tile_n=128` 端到端 9.2% 的优势，对应 linear 部分约 27% 的提升——合理，且与稀释比例自洽。

（注意 `--linear-only` 会从图里删掉任务，也删掉了它们的同步与调度开销，所以 65.9% 是 attention 占比的**上界**，不是精确归因。）

**含义：** A 部分的结论应尽量以 **linear 部分的效应**表述，而不只是 headline 的 ms/token；主扫描最好同时跑 `--linear-only`，否则真实的参数效应可能因为被 attention 淹没而被报成"在噪声内"。真正的解法还是移植 gfx942 decode attention。

## 7. 需要修正计划中的三处

**① 指标不是 decode-only。**
计划把 `Decode: ... ms/token` 定为"全部后续实验的唯一指标"，但它不是 decode-only 的测量。`demo.py:1316-1326`：

```python
avg_time_per_iter = run_time / total_iterations      # prefill + decode 合计
decode_time_est   = decode_iterations * avg_time_per_iter
# decode_iterations == generated_tokens，因此
#   打印的 ms/token == run_time / (prefill_iterations + decode_iterations)
```

打印值恰好是 prefill+decode 合起来的**每次 megakernel 迭代平均墙钟时间**。实测印证：smoke run 里三行全部打印 `10.207 ms`——prefill、decode、combined 是同一个数。

后果：**同一 batch size 内比较配置是有效的**（迭代构成相同）；但**不是干净的 TPOT，也不能跨 batch size 比较**——prefill 迭代数从 bs=1 的约 94 变到 bs=32 的 3，而 prefill 单次迭代远比 decode 贵。A4 必须带着这个前提解读。driver 因此额外记录了 `combined_ms_per_token`、`run_tokens` 和两个迭代计数，保证原始数据可审计。

**② 存在未写进计划的 `GANG_M_TILES_OVERRIDE`。**
`demo.py:471`：`GANG_M_TILES = int(os.environ.get("GANG_M_TILES_OVERRIDE", 0)) or max(1, bs // 16)`。计划只说 `GANG_M_TILES` 由 batch 推导，实际上它可以在任意 batch 下直接指定。A3 用了这个口子（否则按计划只能在 bs=32 下让 `bs//16 == 2` 恰好等于目标值）。

**③ qkv 的整除性算术写错了。**
Qwen3-8B 的 qkv 输出是 `(32 + 2×8)×128 = 6144`，所以 `output_size/8 = 768`，**不是计划写的 512**。无害：候选集 `{32, 64, 128, 256}` 对三个投影仍然都成立（768、3072、512 都能被 256 整除）。

## 8. Part B：MoE 路径（**已完成归因，详见单独文档**）

> **完整内容见 `docs/results/2026-11-16-PartB-MoE归因.md`，修复进展见 `docs/results/2026-11-16-PartB-MoE修复补遗.md`。** 这里只放结论。

**⑤ 第二轮已修好一个真正的 MI300X 专属致命 bug**：`demo_30B_A3B.py` 把 lm_head/argmax 的 grid 设为 `mpk.num_workers`，而 padding 后的 vocab=153600 只在 MI350 的 240 worker 下整除，MI300X 的 296 不整除（余 272）→ 越界。稠密 demo 早有 `argmax_tasks` 保护，MoE demo 没有。修复后 **MoE megakernel 可以执行了**（bs=32 约 25 ms/迭代）。但随即暴露 gate 输出 NaN、split-k 缺归约、路由只覆盖 16 行等三个新缺陷，**输出仍不正确，B4 依然无有效数字**。

**① MoE 路径在 MI300X 上跑不起来。** `demo_30B_A3B.py` 在 bs=1/8/16/32 × gang/非 gang 共 6 种组合下**全部**以 `HIP error: an illegal memory access` 崩溃，且在第一次迭代内。同一份构建下稠密路径正常、PyTorch 路径正常、`TRACE_MOE=1` 显示 11520 条 MoE 任务确实被派发——所以是执行期越界，不是环境问题。该 demo **无 README 文档、无 CI 覆盖**。

**② 结构上确实错配，已量化。** gang MoE 对每个激活专家做 M=BATCH_SIZE 的稠密 GEMM，只在 epilogue 按路由跳过写入。实测（`moe_routing_stats.py`，差异化提示词）：

| batch | 激活专家数 | 每专家 token 数 | 行利用率 | 浪费 |
|:---:|:---:|:---:|:---:|:---:|
| 1 | 8（=topk） | 1.0 | **6.25%** | **16.0×** |
| 32 | 26.5 | 10.67 | 33.3% | 3.31× |

计划的 P1 假设成立，且**小 batch 最严重**。

**③ 但按 roofline 这些浪费大半被隐藏。** 算术强度 32 FLOP/byte vs 机器 ridge 353 → 强访存受限。浪费的算力 0.29 ms/iter，藏在 3.24 ms/iter 的访存下限后面。**真正的优化方向是权重访存与调度，不是抠掉浪费的行。**

**④ 我此前用均匀路由算的 13.9× 是错的**，实测路由偏斜（头部专家占 10.75%），bs=32 实际是 3.31×。

开始前需记下的两点仍然成立：

**（原）① 待修正的算术。** 计划估计 Mixtral 规模下"约 8× 的浪费"。实际浪费因子是 `num_activated_experts / topk`。Mixtral-8x7B 是 8 专家、topk=2，所以是 **4×**，不是 8×。（计划里"每专家平均 2 个 token"本身是对的：B=8、topk=2 时共 16 次分配、摊到 8 个专家上平均 2 个。）另：计划 §3.2 的"专家权重 3.15 MB/个"也偏小——实际 W13=6.29 MB + W_down=3.15 MB = **9.44 MB**。

**② 已核对的准入条件**（模型配置已实际查询）：

| 模型 | hidden | 2×inter | 门禁 | 显存(bf16) |
|---|---|---|---|---|
| Qwen3-30B-A3B | 2048 | 1536 | `1536%64==0` ✓、`2048%256==0` ✓ | 约 57 GB，**已下载** |
| Mixtral-8x7B | 4096 | 28672 | `28672%64==0` ✓、`4096%256==0` ✓ | 约 93 GB，192 GB 放得下 |

**③ 已有可用的观测手段。** `TRACE_MOE=1` 会打开 `-DMPK_TRACE_MOE_DISPATCH`，在 `persistent_kernel.cuh:1736` 打印 `[MOE_DISPATCH] sched=.. xcd=.. worker=.. expert_offset=..`，可直接支撑 B3（每 XCD 的专家/任务放置）。B1（每专家 token 直方图）需要从 `moe_routing_indices` / `moe_mask` 取数；`mpk.new_tensor` 走的是 `attach_cuda_tensor`，目前没找到 python 侧的读回接口，因此更省事的做法是**用 `--use-mirage` 关闭时的 PyTorch 路径挂 hook 统计路由**（路由是隐状态的确定函数，两边输入相同则结果相同），必要时再与 MPK 路径交叉验证。

## 9. 下一步建议（按价值排序）

1. **把 `paged_attention_minimal_decode` 移植到 gfx942**（用 2×16x16x16 MFMA 替代 16x16x32，并为 gfx942 的手调 swizzle 布局模拟 transposed LDS 读）。一次解决两个问题：消掉 66% 的 attention 稀释，解锁 bs=64。
